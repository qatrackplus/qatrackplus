# QATrack+ Release Notes #

Release notes are located at http://docs.qatrackplus.com/en/latest/release_notes.html

## v4.0.2

* **Docker**: Docker hosting is supported on Linux only, with Docker Engine 23.0+ and Docker Compose 2.17+. Windows and Docker Desktop are not supported; on a Windows server, use the Windows Server installation, which doesn't use Docker. The Docker installation guide has been reorganised into setup, configuration, data and backups, day-to-day operation and development, and its out-of-date parts fixed (the Django shell command, removing a site safely, and the backup time, which is now 4 AM in QATrack+'s own time zone). It draws on Vincent Leduc's reorganisation of the Docker docs in [#866](https://github.com/qatrackplus/qatrackplus/pull/866).
* **Docker**: Docker Compose 2.17 and Docker Engine 23.0 are now required. Check with `docker compose version` before your first `git pull` to 4.0.2: with an older Compose, the commands that build or create containers (`up`, `build`, `run` and others) stop with *Additional property additional_contexts is not allowed*. Running containers keep running, but 4.0.2 can't be built or started until Docker is updated, and until then other commands such as `logs` and `stop` need `-p qatrackplus` (`docker compose -p qatrackplus stop`).
* **Docker**: `deploy/docker/.env` is no longer tracked by git, because it holds your database password. Before your first `git pull` to 4.0.2, copy your `.env` aside and back as described in the Docker upgrade guide; later pulls leave it alone.
* **Docker**: QATrack+'s settings (email, time zone, HTTPS, sessions, QC display options, ADFS, Active Directory / LDAP and more) can now be set in `deploy/docker/.env`; `.env.example` documents each one. The image now includes LDAP support.
* **Docker**: The secret key is now kept in a volume, or taken from `SECRET_KEY` in `.env`, so rebuilds never sign users out. 4.0.0 and 4.0.1 kept it in `deploy/docker/user-data/secret_key.txt`: copy it into `.env` before the first start of 4.0.2, as the Docker upgrade guide shows, or every user is signed out once.
* **Docker**: When `SECRET_KEY` is not set in `.env`, `docker compose logs django` now says on each start where the generated key is kept. The nightly backup does not include it; the Docker installation guide shows how to copy it into `.env`, so that losing the volume cannot sign everyone out.
* **Docker**: The upgrade guide's `git stash` steps keep local changes such as a different port in `compose.yaml` across `git pull`.
* **Docker**: Scheduled notifications, scheduled reports and the emails they send now run: a new `django-q` service runs QATrack+'s background tasks, which Docker installations had no process for.
* **Docker**: HTTPS works: with `HTTP_OR_HTTPS=https` and your certificate in `deploy/docker/user-data/ssl`, nginx serves QATrack+ over HTTPS and redirects HTTP to it.
* **Docker**: A database client, reporting tool or SSH tunnel can now connect to PostgreSQL, if you turn it on: list the new `compose.db-port.yaml` in `COMPOSE_FILE` in `deploy/docker/.env`, as `.env.example` shows. It is then published on `127.0.0.1`, port 5434, for this server only; until then, nothing is published ([#866](https://github.com/qatrackplus/qatrackplus/pull/866), thanks to Vincent Leduc).
* **Docker**: Active Directory sign-in over LDAPS works with a directory certificate from your organization's own CA: copy the CA (PEM) into `deploy/docker/user-data/ldap` and set `AD_CERT_FILE=/etc/qatrack/ldap/ca.pem` in `.env`. A certificate from a public CA needs no file.
* **Accounts**: QATrack+ now warns at startup (`qatrack.W011` to `qatrack.W013`) when `AD_CERT_FILE` names a file that is missing, unreadable or not PEM, instead of every LDAPS sign-in failing with *Unable to contact LDAP server*. The site still starts.
* **Docker**: The site no longer answers 502 after an upgrade recreates the django service, and a slow first start (database migrations on slow storage) no longer stops `docker compose up` before nginx starts: django now has up to 10 minutes.
* **Docker**: nginx answers only the hosts in `ALLOWED_HOSTS`, accepts uploads up to 100 MB (was 1 MB), and every service's container output (`docker compose logs`) is capped at 50 MB.
* **Logging**: QATrack+'s log files (`debug.log`, `auth.log`, `migrate.log`, `django-q2.log`) now rotate at 10 MB; before, they grew without limit. On Docker they are kept in a `logs-volume` volume and survive upgrades.
* **Background tasks**: Background tasks can run for up to 5 minutes, up from 1, so a scheduled report whose PDF takes more than a minute to make is no longer stopped.
* **Docker**: Links in emails and reports now point to your site instead of `http://example.com`: the site record is filled in from `SITE_DOMAIN` (or the first host in `ALLOWED_HOSTS`) and `SITE_NAME` in `.env`. A domain and name already set in the admin are kept, unless `SITE_DOMAIN` or `SITE_NAME` is set in `.env`: those replace them on every start, so leave them commented out if you manage them in the admin.
* **Docker**: Follow-up emails from *QC Completed* notices, which were queued but never sent on Docker, are all sent when background tasks first run. The Docker upgrade guide shows how to remove them first.
* **Docker**: The QATrack+ application container no longer runs as root. Existing media and static files are re-owned automatically on the next `docker compose up -d`; the commands you run do not change.
* **Docker**: `compose.override.yaml` is now `compose.dev.yaml` and is no longer applied automatically, so plain `docker compose` runs the code built into the image. Developers use `docker compose -f compose.yaml -f compose.dev.yaml` with their own ids in `.env`. QATrack+'s log files are no longer written to the checkout's `logs` folder (except with `compose.dev.yaml`).
* **Docker**: The Docker image installs exactly the dependency versions in `uv.lock`, the same versions the test suite runs against.
* **Docker**: Calculation procedures can use your own Python packages: list them in `deploy/docker/site-requirements/requirements.txt` and run `docker compose build`. A package that needs a different version of one of QATrack+'s dependencies stops the build instead of changing it.
* **Docker**: Docker images no longer contain your `.env` file, local settings, uploaded files or database dumps. Rebuild any QATrack+ image you have copied to a registry or another machine.
* **Docker**: Backups can now be restored with `restore-db` and `restore-media`, which check the whole backup and ask for confirmation first, including backups made by 4.0.0 and 4.0.1. A restore that fails or is stopped leaves the current database and uploaded files as they were. An interrupted backup no longer leaves a file that looks complete, and a backup can't run during a restore. Backups are now readable only by root on the server, and the first backup after the upgrade does the same to older ones, so copy them with `sudo`.
* **Docker**: The nightly backup moves from 2 AM UTC to 4 AM local time, in `TIME_ZONE` from `.env`, and names its files in that local time instead of UTC. No time zone changes its clocks for daylight saving at 4 AM, so it runs once every night, all year. With `TIME_ZONE` unset, that is QATrack+'s default, America/Toronto, so set it if your site is elsewhere. Backups from before the upgrade keep their UTC names (`ls -lt` lists them newest first), and the first backup after the upgrade may come up to a day sooner or later than usual. Re-time any job that copies the backups off the server at a time chosen to follow the old 2 AM UTC backup.
* **Docker**: QATrack+'s uploaded files, log files, generated secret key and backups can be kept in folders on the server instead of Docker volumes: set `QATRACK_MEDIA_DIR`, `QATRACK_LOGS_DIR`, `QATRACK_USER_DATA_DIR` or `QATRACK_BACKUPS_DIR` in `.env`. Nothing changes unless you set one. Every service, backups and restores included, uses the same folder, and it is given to the QATrack+ user on each start, so QATrack+ only uses a folder that is empty or marked as its own, not inside another of its folders, and holding neither another of them nor a backup; otherwise it does not start, and changes nothing. A file with a second name (a hard link) is never handed over. For a site already in use, copy the data across first, as the Docker installation guide shows. Based on the `/app_data` layout proposed in [#866](https://github.com/qatrackplus/qatrackplus/pull/866).
* **Docker**: Database dumps in `deploy/docker/backups/` and `.env` files (other than the `.env.example` templates) are now ignored by git.
* **Docker**: Files under `deploy/docker` always check out with LF line endings, whatever git's `core.autocrlf` setting.
* **QA**: Superusers and users with "Can view tli and utc not visible to user's groups" now see QC from all groups in the Perform QC lists, trees and unit chooser ([#883](https://github.com/qatrackplus/qatrackplus/pull/883)).

## v4.0.0 Recent Fixes

* **Service Log**: Service Event Templates can now be shared across different machines and modalities. When selecting a template, only the Return to Service tests that apply to the chosen unit will be added to the form ([#829](https://github.com/qatrackplus/qatrackplus/issues/829)).
* **QA**: Fixed an issue where resuming an autosaved QC session could display the wrong start date and time.
